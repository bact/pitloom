### `card-malformed`

- **Level**: WARNING.
- **Means**: The YAML frontmatter at the top of a card (the block between two
  --- lines) does not parse: a model card beside a local model, a dataset's own
  card, or a Hugging Face dataset card a Hub model lists. The line gives what
  the parser reported.
- **SBOM effect**: thinner: the SBOM says less than reading the input would.
- **Pitloom did**: Used nothing of the frontmatter and went on: a model card
  sets no license or datasets; a dataset card no license, license_name,
  license_link, version, tags or pretty_name; a Hugging Face dataset card no
  license or keywords (its description is still read from the card's text).
- **Tell the user**: which card's frontmatter is not valid YAML and what the
  parser reported, as the line says. They fix the card and generate again; a
  Hugging Face dataset card only its maintainers can fix. Do not edit the card
  for them; ask first, and with nobody to ask, report it only.
- **Lines**:

  ```text
  WARNING: FILE=<file>: <card> frontmatter is not valid YAML; <failure> [card-malformed]
  ```

### `dir-unlistable`

- **Level**: WARNING.
- **Means**: A directory could not be listed (no read or search permission): the
  files under it were not seen.
- **SBOM effect**: thinner: the SBOM says less than reading the input would.
- **Pitloom did**: Went on without them: file discovery leaves them out of the
  SBOM (a build backend that lists before it excludes can name a directory it
  would leave out anyway); a dataset directory gets no hash (Evidence:
  not_measured | Reason: dir-unlistable); ID registry indexing leaves them out
  of the index; a model or dataset card in it is not found.
- **Tell the user**: which directory could not be listed and what the system
  reported, as the line says. They give the account Pitloom runs as read and
  search access to it and generate again. Do not change permissions or
  ownership, or copy or move files, for them; ask first, and with nobody to ask,
  report it only.
- **Lines**:

  ```text
  WARNING: DIR=<dir>: could not list <use>; <failure> [dir-unlistable]
  ```

### `field-not-recordable`

- **Level**: INFO.
- **Means**: A model holds a value for a G7 SBOM for AI element that SPDX 3.0.1
  has no property for (the model architecture).
- **SBOM effect**: weaker: what the SBOM says is less sure.
- **Pitloom did**: Wrote the value in the broader property the line names
  (ai_typeOfModel, after the type), or did not record it; the SBOM is otherwise
  unchanged.
- **Nothing to do**: SPDX 3.0.1 has no property for the element; the line says
  where its value is written, if anywhere.
- **Lines**:

  ```text
  INFO: FORMAT=<format> FILE=<file>: no SPDX 3.0.1 property: <elements> [field-not-recordable]
  ```

### `file-unreadable`

- **Level**: ERROR, WARNING. As an ERROR, the command stops for that input and
  writes nothing for it (exit 1).
- **Means**: A file Pitloom found or was named could not be read: the operating
  system refused it (no read permission, a directory above it without search
  permission, a file another program holds open on Windows) or the read failed
  (an I/O error, a file that is no regular file once opened).
- **SBOM effect**: thinner: the SBOM says less than reading the input would.
- **Pitloom did**: Read nothing more of it and went on without what it holds, as
  the line says what it was read for: a file scan leaves the file out of the
  SBOM (loom embed-wheel keeps it, with the wheel's own hash); a hash leaves no
  verifiedUsing (a model's ID registry lookup is then not gated; a dataset's
  provenance says Evidence: not_measured | Reason: file-unreadable); a project
  setting's field is not set from the file; the usage scan records no model
  reference from it; ID registry indexing leaves it out of the index; no
  dependency pins are read from a lock file; a model whose header could not be
  read is not listed as an AI model; a model or dataset card sets none of the
  fields it states. As an ERROR, the call that named the file raises (a
  Croissant document: the dataset declaration fails).
- **Tell the user**: which file could not be read and what the system reported,
  as the line says. They give the account Pitloom runs as read access to it (or
  close the program that holds it), or restore a damaged copy, and generate
  again. Do not change permissions or ownership, or copy, move or replace the
  file, for them; ask first, and with nobody to ask, report it only.
- **Lines**:

  ```text
  WARNING: FILE=<file>: could not read <use>; <failure> [file-unreadable]
  WARNING: FILE=<file>: could not read for <field>; <failure> [file-unreadable]
  WARNING: FORMAT=<format> FILE=<file>: could not read header; <failure> [file-unreadable]
  ERROR: FILE=<file>: could not read <use>; <failure> [file-unreadable]
  ```

### `file-unreadable/not-utf8`

- **Level**: WARNING.
- **Means**: A text file Pitloom read is not UTF-8, the encoding it must be in:
  a requirements file or a file a setup.cfg directive lists, or a Python file
  read for the model usage scan.
- **SBOM effect**: thinner: the SBOM says less than reading the input would.
- **Pitloom did**: Went on without what the file holds: the field is not set
  from it, or the usage scan records no model reference from it.
- **Tell the user**: which file is not UTF-8 and what the decoder reported, as

  only.
- **Lines**:

  ```text
  WARNING: FILE=<file>: could not read <use>; not UTF-8: <failure> [file-unreadable/not-utf8]
  WARNING: FILE=<file>: could not read for <field>; not UTF-8: <failure> [file-unreadable/not-utf8]
  ```

### `file-unreadable/outside-project`

- **Level**: WARNING.
- **Means**: A file a project setting names, or a licence file, leads outside
  the project directory (a .. or absolute path, or a symbolic link out), and
  Pitloom reads no file outside it: its content is no part of the project. For
  an installed dependency, the directory is its .dist-info.
- **SBOM effect**: thinner: the SBOM says less than reading the input would.
- **Pitloom did**: Did not read it and went on without what it holds: the field
  is not set from it, or its licence text and copyright notices are not used.
- **Tell the user**: which file lies outside the project and which setting or
  licence file names it, as the line says. They move or copy the file into the
  project, or point the setting at a file inside it, and generate again; for an
  installed dependency, only its maintainers can fix it. Do not move, copy or
  link files, or edit the setting, for them; ask first, and with nobody to ask,
  report it only.
- **Lines**:

  ```text
  WARNING: FILE=<file>: could not read <use>; outside the project directory [file-unreadable/outside-project]
  WARNING: FILE=<file>: could not read for <field>; outside the project directory [file-unreadable/outside-project]
  ```

### `hyperparameter-conflict`

- **Level**: WARNING.
- **Means**: A model states a hyperparameter named parameters, the key the SBOM
  holds its parameter count under.
- **SBOM effect**: none: the SBOM states what the input holds.
- **Pitloom did**: Recorded the parameter count (summed from the model's
  tensors, or stated by the Hugging Face Hub) under the parameters key, in place
  of the model's own value.
- **Nothing to do**: the parameters entry is the parameter count, as the
  package's comment says; the model's own value is still in the model.
- **Lines**:

  ```text
  WARNING: FORMAT=<format> FILE=<file>: hyperparameter parameters replaced by the parameter count [hyperparameter-conflict]
  ```

### `json-malformed`

- **Level**: ERROR. As an ERROR, the command stops for that input and writes
  nothing for it (exit 1).
- **Means**: A JSON document Pitloom was given to read (a Croissant file) does
  not parse, or its top level is not an object.
- **SBOM effect**: not-written: no SBOM is written for the input.
- **Pitloom did**: Read nothing of it: the call raises ValueError carrying the
  code, and the dataset declaration (loom.add_dataset with croissant=, or
  read_croissant) fails.
- **Tell the user**: which document is not valid JSON, or not a JSON object, and
  what the parser reported, as the line says. They fix or replace it and run
  again. Do not edit or replace the document for them; ask first, and with
  nobody to ask, report it only.
- **Lines**:

  ```text
  ERROR: FILE=<file>: not valid JSON <use>; <failure> [json-malformed]
  ERROR: FILE=<file>: not a JSON object <use> [json-malformed]
  ```

### `lfs-pointer`

- **Level**: ERROR, WARNING. As an ERROR, the command stops for that input and
  writes nothing for it (exit 1).
- **Means**: A file is a Git LFS pointer: a small text file standing in for
  content the checkout does not have (made or cloned without Git LFS).
- **SBOM effect**: thinner: the SBOM says less than reading the input would.
- **Pitloom did**: Listed each pointer file by the SHA-256 the pointer states
  for its content, with the stated size in the hash comment (no SHA-512, no
  content type); did not read the content or list it as an AI model. One warning
  names the first file in sorted order and, for more than one, how many.
- **Tell the user**: the SBOM still identifies each file by its content's
  SHA-256 but lacks what reading it gives (AI model details, SHA-512). If they
  want them, they run 'git lfs pull' in the checkout (for a Git URL: clone it
  with Git LFS and run Pitloom on that directory) and generate again. Do not
  pull, clone or regenerate for them; ask first, and with nobody to ask, report
  it only.
- **Lines**:

  ```text
  WARNING: FILE=<file>: Git LFS pointer, content not read<count>; run 'git lfs pull' for the content [lfs-pointer]
  WARNING: FILE=<file>: Git LFS pointer, content not read<count>; clone with git lfs, then run on the directory [lfs-pointer]
  ERROR: '<path>': header is a Git LFS pointer, content not pulled (oid sha256:<oid>, size <size>); run 'git lfs pull' [lfs-pointer]
  ```

### `lfs-pointer-malformed`

- **Level**: ERROR, WARNING. As an ERROR, the command stops for that input and
  writes nothing for it (exit 1).
- **Means**: A file starts with the Git LFS pointer line but is not a valid
  pointer: damaged, cut short, or 1 KiB or larger.
- **SBOM effect**: thinner: the SBOM says less than reading the input would.
- **Pitloom did**: Listed it as an ordinary file, hashed as it is, not as an AI
  model.
- **Tell the user**: the file is neither its content nor a valid pointer: they
  check it out again or replace it with the real content, then generate again.
  Do not change the file for them.
- **Lines**:

  ```text
  WARNING: FORMAT=<format> FILE=<file>: header looks like a Git LFS pointer but is not a valid one; not listed as an AI model [lfs-pointer-malformed]
  WARNING: FILE=<file>: header looks like a Git LFS pointer but is not a valid one; not listed as an AI model [lfs-pointer-malformed]
  ERROR: '<path>': header looks like a Git LFS pointer but is not a valid one [lfs-pointer-malformed]
  ```

### `lfs-pointer/shipped`

- **Level**: WARNING.
- **Means**: A built wheel or sdist holds Git LFS pointer files where the
  content belongs: it was built from a checkout without the LFS content.
- **SBOM effect**: none: the SBOM states what the input holds.
- **Pitloom did**: Listed each file as the artefact holds it, with the hashes of
  the pointer text.
- **Tell the user**: the artefact is probably broken: whoever installs it gets
  pointer text, not the files. If the content belongs in it, they run 'git lfs
  pull' before building and build again, before publishing. Do not rebuild for
  them.
- **Lines**:

  ```text
  WARNING: FILE=<file>: Git LFS pointer shipped<count>; the build did not pull LFS content [lfs-pointer/shipped]
  ```

### `library-missing`

- **Level**: ERROR, WARNING. As an ERROR, the command stops for that input and
  writes nothing for it (exit 1).
- **Means**: A library Pitloom needs for a step is not installed: an optional
  extra for a model reader, the Hugging Face Hub, SPDX 3 validation,
  --allow-build or magika content types.
- **SBOM effect**: thinner: the SBOM says less than reading the input would.
- **Pitloom did**: For a model file, listed the model by its file, format and
  hashes only (a format-only entry, named after its file), without its metadata.
  For any other step, did not run it: no SBOM of a Hugging Face model, no
  validation; --allow-build found the files without a build, as its Build: lines
  say. Installed nothing.
- **Tell the user**: which models or which step went without the library and
  which extra installs it, as the line names it (pitloom[ai] installs every
  model reader and the Hugging Face Hub client). They install it where Pitloom
  runs (with uvx or pipx, in the --from or --spec requirement) and run again; a
  model reader then runs on each such file, so only for files they trust. Do not
  install anything or run again for them; ask first, and with nobody to ask,
  report it only.
- **Lines**:

  ```text
  WARNING: FORMAT=<format> FILE=<file>: required library not installed; install <requirement> [library-missing]
  ERROR: required library not installed: <module>; install <requirement> [library-missing]
  ```

### `library-unusable`

- **Level**: ERROR, WARNING. As an ERROR, the command stops for that input and
  writes nothing for it (exit 1).
- **Means**: A library Pitloom needs for a step is installed but fails to
  import: a broken or partial install, a library it needs in turn missing, or a
  build for another Python or platform.
- **SBOM effect**: thinner: the SBOM says less than reading the input would.
- **Pitloom did**: For a model file, listed the model by its file, format and
  hashes only (a format-only entry, named after its file), without its metadata.
  For any other step, did not run it: no SBOM of a Hugging Face model, no
  validation, no SBOM with magika content types (method magika); with method
  auto, every file's content type from its extension, said once a run. Installed
  nothing.
- **Tell the user**: which models or which step went without the library, what
  the import reported and which extra reinstalls it, as the line names it. They
  reinstall it where Pitloom runs (with uvx or pipx, in the --from or --spec
  requirement) and run again; a model reader then runs on each such file, so
  only for files they trust. Do not install anything or run again for them; ask
  first, and with nobody to ask, report it only.
- **Lines**:

  ```text
  WARNING: FORMAT=<format> FILE=<file>: required library failed to import: <error>; reinstall <requirement> [library-unusable]
  ERROR: required library failed to import: <module>: <error>; reinstall <requirement> [library-unusable]
  WARNING: required library failed to import: <module>: <error>; content types from file extensions; reinstall <requirement> [library-unusable]
  ```

### `model-field-conflict`

- **Level**: WARNING.
- **Means**: A model states one key twice: a GGUF file states the length of an
  array as a key of its own, or an ONNX file repeats a metadata_props key.
- **SBOM effect**: none: the SBOM states what the input holds.
- **Pitloom did**: Recorded what the file's own reader sees: the GGUF key as the

- **Nothing to do**: the SBOM states what the model's own reader sees; the other
  value is still in the model.
- **Lines**:

  ```text
  WARNING: GGUF key <entry> is in the file; the length of array <name> is not a property [model-field-conflict]
  WARNING: ONNX metadata_props: <number> key(s) appear more than once; kept the last value of each: <name> [model-field-conflict]
  ```
