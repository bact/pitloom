# Pitloom's catalogued messages

See also: `../SKILL.md` (which holds the rule: explain and relay, never run
the fix), `known-limitations.md` (what Pitloom does not cover, and the stub
model).

A Pitloom stderr line that ends in a `[code]` is catalogued: find the code in
the table below, then read the page it links (one page per topic) for what it
means, what Pitloom did and what to tell the user. Quote the
line as printed. You explain the line and relay its advice; you do not run the
fix yourself (no `git lfs pull`, no install, no rebuild): ask the user first,
and with nobody to ask, report it only. A line without a code is a
summary, a `-v` `KEY=VALUE` detail, another tool's words after its name
(`licenseid: `, `setuptools stderr: `, `fickling: `, `spdx3-validate: `), an
unexpected error's own text, argparse's own text where a Python version words
it differently from the catalogue, or an untagged usage or traceback line;
read it as text. A message that could not be shown prints a fixed text and
keeps its error's code when it had one, so it reads as a line without a code
only when the error had none. The pages are generated from Pitloom's catalogue, so they
say what this version prints.

Pitloom's own lines start `ERROR:`, `WARNING:` or `INFO:`. `WARNING:` marks a
recovered problem or a deviation (a config value normalised, a detector not
installed, an option with no effect for this target); `INFO:` marks normal
status, above all **generation skipped or scoped down**. Neither always fails
the command or reaches the SBOM, so mention each one, even on exit 0 with a
file written.

A quote of a coded line on these pages may leave its frame out
(`Build: `, `FORMAT=<format> FILE=<file>: `): the code names the
line. A quote of an uncoded line matched by its text (a relay, a summary)
shows the frame the line prints, as in
`ERROR: loom fragment validate: spdx3-validate: <line>`.
